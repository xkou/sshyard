# Linux 窗口最大化后卡住：排查总结

## 当前结论

问题描述为：SSHYard 在 Linux 上最大化或还原窗口后，界面出现卡住、点击或选择反馈不更新的现象。当前代码已包含针对重绘、文件列表布局、弹窗层级和输入事件的处理，但现有日志不足以确认唯一根因，也不足以认定问题已经彻底修复。

现阶段需要区分两种情况：画面没有正确更新，以及主线程或一次输入处理确实无法返回。最近一次日志中的最大化操作之后，文件列表仍接收到了点击和框选，主线程心跳正常，没有记录到持续阻塞。不能仅凭“看起来不动”就判断为死锁。

## 证据范围

- 代码基线：本次整理时的 `94b0729`，使用 MyGo `v0.7.4`；诊断与相关处理主要包含在 `3db9097`（`改进`）中。
- 本机日志：应用数据目录中的 `diagnostics.log` 和 `diagnostics.log.1`，合计读取 5,151 条有效 JSON 记录。
- 日志覆盖时间：`2026-11-11T12:03:45Z` 至 `2026-11-12T07:20:34Z`，以下时间均为日志中的 UTC 时间。
- 最近一次启动记录标识为 Linux / amd64、应用版本 `1.1.0`，启用了完整帧重绘，未禁用 GPU。该版本号不能证明运行的二进制与当前源码完全相同。
- 日志经过轮转，并非全部历史；没有与用户确认的故障时刻逐一对应，也没有本次重新进行的桌面交互复现。

## 主要排查方向与已有处理

### 1. GTK / GPU 局部重绘

当前实现将 GTK 的 `GtkGLArea` 在最大化切换时可能更换 framebuffer、导致局部帧保留失效，作为渲染风险处理。此类问题可能表现为悬停、选中等状态已经改变，屏幕却没有同步更新。

已有处理位于 [native_render_linux.go](../native_render_linux.go)：

- Linux 默认设置 `MYGO_PARTIAL=0`，使用完整帧重绘。
- MyGo 在包初始化阶段读取该设置，因此程序在创建窗口、打开凭据存储之前执行一次 `exec`，让设置在下一次初始化时生效。
- 用户显式设置的非空 `MYGO_PARTIAL` 优先。
- 准备完整重绘失败时，`main.go` 尝试通过 `MYGO_GPU=0` 使用软件渲染。

这是当前代码中的防护措施。最近一次日志已开启完整重绘，但没有与明确故障时刻对应的 GPU / 软件渲染对照结果，不能据此宣布 framebuffer 问题就是已证实的根因。

### 2. 最大化后的文件列表布局与控件身份

窗口尺寸和最大化状态变化时，代码更新 UI 的 `revision`；文件表据此重新计算布局，清除旧行几何信息和框选过程状态。文件表保留原有列表状态及稳定的控件 key，避免在尺寸变化时替换整个列表。

已有处理见：

- [internal/app/titlebar.go](../internal/app/titlebar.go)：最大化状态变化时更新 `revision`。
- [internal/app/ui_diagnostics.go](../internal/app/ui_diagnostics.go)：逻辑尺寸变化时更新 `revision`。
- [internal/app/files.go](../internal/app/files.go)：更新宽度和布局代次，重置行几何与框选过程，记录 `files.layout`。
- [main.go](../main.go)：原生窗口 resize 后调用 `Invalidate()` 请求刷新。

日志中同时存在旧实现的 `files.rebind` 和新实现的 `files.layout`，反映了排查期间运行过不同实现。需要按进程和启动时间区分，避免把不同版本的行为混为一谈。

### 3. 弹窗遮挡与输入截获

“点击后没有反应”也可能发生在模态状态已打开、面板却未正确呈现时。

当前 [internal/app/filesheets.go](../internal/app/filesheets.go) 将文件相关弹窗放在工作区、虚拟列表、右侧工具栏和状态栏构建之后统一处理，并为每个 pane 和弹窗类型分配独立身份。弹窗关闭时不调用 `Context.Key`，避免将未消费的 key 留给后续控件。打开后还会请求下一帧，以重新检查最终几何信息。

诊断分别记录 `files.dialog.state` 和 `files.dialog.paint`，用于区分“逻辑上打开”和“到达绘制回调”。绘制回调出现仍不能直接证明最终屏幕内容正确。最近一次收藏弹窗同时具备两种记录，关闭后 `modal_id` 回到 0，因此该段记录不支持模态层一直残留的判断。

### 4. 事件循环阻塞与嵌套事件循环

只看心跳不足以排除所有卡住情况：同步 GTK 操作可能进入嵌套事件循环，心跳仍能执行，但原来的帧或输入处理迟迟不能结束。

当前诊断包含：

| 检测点 | 用途 |
| --- | --- |
| `ui.heartbeat`、`queue_ms` | 判断投递到主线程的任务是否及时执行 |
| `ui.waiting`、`ui.stack` | 心跳任务持续未获响应，等待超过 5 秒时记录一次 Go 栈 |
| `ui.input_stall`、`ui.nested_stack` | 心跳仍可运行，但活动帧或输入派发持续至少 5 秒 |
| `native.pointer`、`native.pointer.done` | 通过相同 `sequence` 对照 GTK 输入派发前后，并查看处理耗时 |
| `pressed`、`drag_active`、`modal_id`、`gtk_grab_type` | 检查按压、拖拽、模态层及 GTK grab 是否残留 |
| `frame_active`、`view_active`、`frame_age_ms` | 区分空闲界面、构建中的界面和迟迟不能结束的帧 |

对应实现为 [internal/diagnostic/log.go](../internal/diagnostic/log.go)、[internal/gtkfix/input_linux.go](../internal/gtkfix/input_linux.go) 和 [internal/app/input_diagnostics.go](../internal/app/input_diagnostics.go)。自绘窗口按钮还通过异步调用执行原生窗口操作，避免直接在触发按钮的视图帧内完成窗口操作；这同样不构成对根因的证明。

## 后续复现与判断方法

1. 从托盘菜单完全退出 SSHYard，再启动待验证版本，确认新的 `app.start` 记录及渲染模式，避免继续使用旧进程。
2. 打开文件面板，在普通窗口中确认点击、框选、收藏弹窗和工具栏操作可用。
3. 最大化窗口，重复这些操作；还原后再次重复。记录发生异常的准确时间、操作、是否仍可移动窗口和使用键盘。
4. 分别验证自绘标题栏和系统标题栏；标题栏方式在创建窗口时读取，更改后需完全退出并重启。
5. 需要进一步隔离渲染因素时，分别使用完整 GPU 重绘和 `MYGO_GPU=0` 软件渲染做相同操作。每轮保留启动模式和对应时间；对照结果出现前不下根因结论。
6. 检查同一进程、同一时段的输入、布局、模态和心跳记录，按下表缩小范围。

| 故障时的记录 | 优先排查方向 |
| --- | --- |
| 持续 `ui.waiting`，并出现 `ui.stack` | 主线程未及时处理任务，检查栈中的阻塞点 |
| 心跳正常，但出现 `ui.input_stall` | 嵌套 GTK 循环、未结束的帧或输入处理 |
| 有 `native.pointer`，同一 `sequence` 长期没有完成记录 | GTK 派发或其调用链；需同时考虑日志是否丢失、轮转或进程退出 |
| 原生输入正常，预期控件没有相应处理记录 | 控件命中、焦点、grab、模态遮挡或布局身份 |
| 选择数量、操作状态和绘制记录变化，屏幕反馈不变 | GPU 呈现、重绘和 framebuffer；需桌面复现确认 |
| 心跳正常，窗口失焦，没有新输入，帧计数不变 | 可能只是正常空闲，需在主动交互期间重新观察 |

默认日志目录为 `~/.config/SSHYard/`，设置 `SSHYARD_DATA_DIR` 时使用对应目录。收集 `diagnostics.log` 和 `diagnostics.log.1`，同时注明故障时刻和运行版本。日志按 2 MiB 轮转，后台队列满时可能丢弃记录，`dropped` 字段可辅助判断证据完整性。

诊断只记录窗口几何、计数、数字身份、运行状态和去除参数值的 Go 栈；不要为排查额外记录文件名、目录路径、终端内容或凭据。更多事件说明见 [diagnostics.md](diagnostics.md)。
